# GitHub 成功案例学习报告

调研日期：2026-09-15

## 调研目的

本次调研不以复制功能或代码为目标，而是寻找已经被真实项目验证过的产品结构、交互方式和工程做法，并判断哪些适合当前中国象棋 AI 教学软件。评价优先级依次为：象棋正确性、教学闭环、引擎可靠性、棋谱研究效率、桌面端长期使用体验。

## 成功案例的共同规律

### 1. 局面节点是核心，而不是棋步文本

成熟棋谱工具把每个历史节点同时关联到 FEN、走法、评论、引擎评价和分支。用户点击节点后，棋盘、回合、引擎分析与说明一起切换。当前项目已有 `VariationTree` 数据层，下一步应优先完成 UI 接入，而不是继续增加孤立功能。

### 2. 引擎数据要可追溯

一次分析必须归属于明确的 FEN、行棋方、节点、参数和引擎版本。评价条只解决“谁优”，评价趋势和节点颜色才能帮助用户发现“哪一步开始出问题”。缓存不能让旧节点结果覆盖当前节点。

### 3. 教学流程必须延迟答案

训练成功案例普遍允许提示、揭晓和重试。当前产品应固定采用以下顺序：

自己思考 → 区域提示 → 棋子提示 → 候选方向 → 最佳着 → 原理解释 → 沙盘验证

默认界面不显示最佳着箭头；只有进入答案阶段或用户明确要求时才显示。

### 4. 研究与训练需要不同工作流

棋谱研究强调节点、分支、批量分析和注释；训练强调作答、提示消耗、重试和掌握度。两者可以共用规则、引擎和导师证据，但不能共用一套含糊的 UI 状态。

### 5. 无引擎时仍应可用

引擎未安装或崩溃时，合法走棋、棋谱回放、沙盘和本地记录仍应工作。界面需要把“规则判断”“引擎判断”“AI 解释”三种能力的状态分开显示，避免让用户误以为整个软件失效。

## 对当前项目的具体决策

### P0：可靠性门槛

1. 补齐真实 Pikafish 的 20 个代表性 FEN 验收，覆盖红黑行棋、CP/Mate、MultiPV、合法 PV 和中文记谱。
2. 为新对局加入明确的 `ucinewgame → isready` 生命周期，并测试搜索中止、超时、崩溃重启和程序退出。
3. 所有 UI 分析结果继续校验 `request_id + FEN + position_version + branch_id`，旧结果不得写入新局面。

### P1：把已有能力连成学习闭环

1. 将 `VariationTree` 接入棋谱面板，节点可点击并同步棋盘、FEN、中文着法和当前分支。
2. 分析结果写入节点，增加评价趋势与关键转折点标记；默认隐藏最佳着箭头。
3. AI 导师证据显式携带 `branch_id`、节点 FEN、用户走法、对手最佳回应和已验证 PV。
4. 从任意历史节点进入沙盘，退出后主线不变；不同分支独立保存。

### P2：训练与复盘

1. 建立独立训练状态：作答、提示等级、揭晓、重试、完成状态。
2. 从完整对局的评价变化中筛选关键转折点，生成“为什么不能这么走”练习。
3. 保存完整 FEN 序列、节点评价、MoveAssessment 和导师讲解，使整盘复盘可重复打开。

## 明确不做的事

- 当前阶段不优先开发联网匹配、账号等级和排行榜。
- 不因案例拥有某项功能就直接复制；每项功能必须服务“理解为什么”的教学目标。
- 不复制 GPL 项目的源代码、素材或实现细节；若未来分发 Pikafish 或 NNUE，先完成许可证清单和发行合规检查。
- 不用星标数量代替质量判断；案例价值以功能闭环、持续维护和与本项目的相关性为准。

## 验收标准

只有满足以下条件，案例学习才算真正落地：

- 点击任一历史或分支节点后，棋盘、FEN、回合、着法、评价和导师上下文完全一致。
- 黑方行棋时，评价方向、中文说明和推荐路线不发生红黑颠倒。
- 在揭晓之前，UI 不泄露最佳着；每一级提示都比上一级更具体。
- 引擎缺失、超时或崩溃不会冻结 Qt 主线程，也不会破坏棋谱。
- 所有新增流程都有自动化测试，并经过原生 Windows GUI 实测。
